## S.O.L.I.D. PRINCIPLES FOR RUST

### S - Single Responsibility
- One purpose per module/struct/function
- Separate data (`struct`) from behavior (`impl`)
- Use NewType pattern: `struct UserId(u64)`

### O - Open/Closed
- Prefer Traits over Enums for extensibility
- Avoid large `match` statements on growing variants
- Use `Box<dyn Trait>` or generics for polymorphism

### L - Liskov Substitution
- Any `T: MyTrait` must work correctly for all implementations
- No unexpected panics in trait implementations

### I - Interface Segregation
- Prefer many small traits over "God Traits"
- Don't force unused method implementations

### D - Dependency Inversion
- Depend on abstractions (Traits), not concretions
```rust
// Good
fn execute<T: Database>(db: &T)

// Bad
fn execute(db: &PostgresDb)
```

## CODING STANDARDS

### Syntax Conventions
```rust
// Variable initialization
let variable_name: VariableType = value;

// Section headers
// == SECTION NAME // ==

// Public API docs
/// Brief description
///
/// # Example
/// ```
/// code_example();
/// ```
```

### Error Handling
- **NEVER** use `.unwrap()` or `.expect()` in production
- Use `Result<T, E>` with `thiserror` (lib) or `anyhow` (app)
- Propagate errors with `?` operator
- Define errors in `error/` module hierarchy

### Safety & Performance
- Prefer safe Rust; document any `unsafe` heavily
- Minimize `.clone()` unless `Copy` types
- Prefer channels over `Arc<Mutex<T>>`
- Use `Option`/`Result` combinators over explicit `match`

## ACTIX-WEB PATTERNS

### Route Organization
```rust
pub fn init(cfg: &mut web::ServiceConfig) {
    cfg.service(
        web::scope("/api/feature")
            .service(handler_a)
            .service(handler_b)
    );
}
```
**⚠️ Order matters:** More specific routes before less specific.

### Handler Pattern
```rust
/// POST /api/feature/action
#[post("/action")]
#[instrument(skip(app, req))]
pub async fn action_handler(
    app: web::Data<App>,
    req: HttpRequest,
    body: web::Json<RequestDto>,
) -> AppResult<HttpResponse> {
    // 1. Extract/validate
    let user_id = get_user_id_from_session(&app, &req)?;
    validate_request(&body.0)?;
    
    // 2. Build use case input
    let input = UseCaseInput { /* ... */ };
    
    // 3. Execute use case
    let use_case = MyUseCase::new(Arc::clone(&app.service));
    let result = use_case.execute(input).await?;
    
    // 4. Return response
    Ok(HttpResponse::Ok().json(ResponseDto::from(result)))
}
```

### Use Case Pattern
```rust
pub struct MyUseCase {
    service: Arc<MyService>,
}

impl MyUseCase {
    pub fn new(service: Arc<MyService>) -> Self {
        Self { service }
    }

    pub async fn execute(&self, input: Input) -> Result<Output, Error> {
        // Validation
        self.validate(&input)?;
        
        // Business logic
        self.service.do_something(input).await
    }
}
```

## TESTING REQUIREMENTS

### Data-Driven Test Pattern
```rust
#[cfg(test)]
mod tests {
    use super::*;

    // == Test Case Definition // ==
    struct TestCase {
        name: &'static str,
        input: InputType,
        expected: Result<OutputType, ErrorType>,
    }

    #[test]
    fn test_feature() {
        // == Test Cases // ==
        let cases = vec![
            TestCase {
                name: "success_case",
                input: valid_input(),
                expected: Ok(expected_output()),
            },
            TestCase {
                name: "error_case",
                input: invalid_input(),
                expected: Err(expected_error()),
            },
        ];

        // == Execute // ==
        for case in cases {
            let result = function_under_test(case.input);
            assert_eq!(result, case.expected, "Failed: {}", case.name);
        }
    }
}
```

### Minimum Coverage
- ✅ Success case (happy path)
- ✅ Error case (failure handling)
- ✅ Error message validation

Context: Rust Error Handling

Please follow idiomatic Rust practices regarding error handling. Do not use sentinel errors (e.g., global constants, specific integers like -1, or generic strings) to signal failures.

Instead, define a custom enum to represent error types. This approach allows for:

Type Safety: The compiler ensures all error cases are handled.

Context: Unlike static sentinels, enum variants can carry dynamic data (e.g., which ID failed).

Pattern Matching: It enables the use of match expressions for robust control flow.

Requirement:

Create an enum (e.g., AppError).

Use unit variants for simple errors (acting as type-safe sentinels).

Use tuple/struct variants when context is needed.

(Optional but recommended) Derive thiserror::Error if external dependencies are allowed.

Example Pattern:

Rust

enum MyError {
    // Acts like a sentinel (no data)
    NotFound,
    // Carries context (impossible with simple sentinels)
    InvalidInput { value: String, reason: String },
}
